# R3-D：三维渲染组件

> 本轮产出：`Vec3` / `Mesh` / `Camera` / `Scene3D` / `View3D` 五个新类型，showcase 左侧新增「三维」分组一页（反应釜撬块），测试 +20 例。

## 0. 需求

「实现 3D 的渲染，可以增加 3D 渲染组件，可以加载 3D 图形化，可以对它进行操作、转向，以及 3D 显示某个部件状态。」

翻成工程语言：一个三维视图控件，能装载模型、能旋转缩放平移、能**把某个部件按状态着色**——最后这条是工控 HMI 的真实价值点，其余都是为它服务的。

---

## 1. 前提：这个库没有 GPU

整库的光栅化底座是 **Blend2D，一个纯 2D 引擎**（架构 §3.5，BL* 符号只允许出现在 `Painter.cpp` 与 `Canvas.cpp` 两个 TU 里）。所以三维只能是软件渲染：变换、剔除、排序都在 CPU 上，最后落到 `Painter::fillTriangle`。

裁定的是**画家算法**，不是自写 z-buffer 软光栅。理由三条：

1. z-buffer 要往 `Surface` 写像素，等于在两个 TU 之外**开出第三条像素路径**，直接撞 §3.5；
2. 会丢掉 Blend2D 已有的抗锯齿、裁剪，以及 `OffscreenImage` 通路——而离屏通路是 golden 测试和人工目视复核的唯一入口；
3. 深度缓冲要一块与视口同尺寸的内存，与「热路径零分配」对立。

---

## 2. 画家算法在这里是**精确**的，不是将就

这一节是整个设计的承重墙。

> **凸闭合体 + 背面剔除 ⇒ 幸存的正面集合是视平面上的一张高度场。**
> 于是**同一物体的面之间不可能互相遮挡**，它们之间的顺序**根本不重要**。

排序因此降级成"给**物体**排序"——几十次比较，不是几千次。`MeshBuilder` 的每一个 `addXxx()` 只产出一个凸闭合体，并记下它的面区间与包围球。

**残留说清楚**：两个**相互穿插**的物体仍会按质心排错。在这个库的语义里那是**建模错误**——泵不会穿过罐。仅仅**相切**的物体（封头坐在筒体上）被一个平面分开，永远排对。

⚠️ 这条约束不是纸面的。示例页第一版用**整球**当封头，半个球埋在筒体里，渲染出来容器发虚、像个能看见内壁的敞口桶。**修法不是改渲染器，是加一个半球封头图元**（`addDome`，半椭球 + 平底盘，仍是凸闭合体），让它与筒体只共享一个圆。

---

## 3. 「可以加载」是用**所有权方向**兑现的，不是用解析器

`Mesh` 定义成**非拥有的数据窗口**：三个指针、三个计数，指向**应用持有**的数组。于是：

* 同一份几何给两个视图、在厂区里摆四十处，零拷贝；
* **外部加载器不需要库的任何支持**——谁想要 OBJ/STL/厂商格式，自己解析进自己的 vector，再套一个 `Mesh` 上去，库里没有一行代码知道那个格式存在过。

库内不做解析器，是因为它会**同时**带进三笔代价：不可信输入面、不可控的三角形数（直接击穿预算）、以及"数据不复制"失效（解析器天然要拥有它产出的东西）。库内加载器排下一轮。

## 4. 部件状态是 **PUSH**，与表格的 PULL 相反——理由必须写下来

`Scene3D::setPartState(PartId, PartState)`，`addPart("P-101")` 返回稳定 id，**运行期绝不按字符串寻址**。

与上一轮的表格**故意相反**，所以理由写进了头注释，免得后人来"修一致性"：

| | 表格 | 三维 |
|---|---|---|
| 数量 | **无界**（20 万行） | **有界**（一个撬块几十个部件） |
| 每帧涉及 | 只有一屏 | 全部 |
| 变化频率 | 随时 | **事件驱动，极少** |
| 结论 | 拉取才免拷贝 | 拉取只换来"每部件每帧一次虚调用"的纯亏损 |

架构 §4 直接判：不用不付代价。

**连带的好处**：因为是推送，`scene3d` **一个虚函数都不需要**，于是**给门 lint 的 P1 名字集合新增 0 条**——上一轮"新虚名会把全库同名调用变成门候选"的教训，这轮从设计上绕开了。

**与 TagId 打通，不与 DataHub 打通**：`bindPart(PartId, TagId)` 只是元数据。阈值→状态的映射是**工艺工程**，写在应用里；示例页在 UI 线程的动画 tick 上把釜温翻译成状态，于是 §3.11（工作线程不得碰 Widget）自动满足。

## 5. 拾取：**你点到的一定是你看见的那一个**

不做颜色 ID 缓冲（要多一遍离屏渲染 + 第二条光栅路径），不做三维射线求交（要逆矩阵与反投影，而且**可能与画出来的东西不一致**）。

做法是**复用当帧已经投影并排序好的面表**，在屏幕空间由前向后做点在三角形内测试。它与绘制共用同一份数据、同一个背面剔除判据，所以两者**在构造上不可能不一致**。首帧绘制前返回无效 id，**不为拾取而按需渲染**。

## 6. 三条可检验的预算，以及一条比它们都值钱的判据

| 项 | 断言 |
|---|---|
| 背面剔除 | 一个凸闭合体从任何视角提交的面 **≤ 一半** |
| 每帧分配 | 连画 5 帧的分配次数 **不超过** 画 1 帧的 5 倍（缓冲区在 `setScene` 一次性定尺寸） |
| 部件读取 | 每帧每部件**至多 1 次**（`Scene3D` 自计；一个部件三个物体的场景会抓出"按物体查表"的写法） |

**但本轮最值钱的一条测试是绕序判据**：

> 对**凸**体，每个面的外法线必须**背离物体质心**。

它是精确、机械、一个循环覆盖全部图元的。加上它之前，我靠手推叉乘写绕序——**六个图元里错了五个**（圆柱/管道/法兰的侧壁、球面、圆锥底盖、封头平底盘；只有 box 是对的）。错的表现不是"消失"，而是**渲染出远侧的内壁**，看上去像一个能看穿的实体——所有单元测试照样全绿，是**截图**先发现的。判据落地后，五处一次改对。

**教训写死**：几何绕序不该靠人推导，该靠一条判据。

## 7. 两个自己踩出来的坑，都记在这里

**一、抗锯齿接缝是覆盖率问题，不是审美问题。** 两个共边三角形各自抗锯齿，沿共享边分别覆盖 `a` 与 `1-a`，合成后仍有最多 `a(1-a)` ≈ 25% 的背景漏出来。在圆柱壁上，每个四边形的对角线都成了一条细缝，透视下汇聚成放射状纹路，整个筒体看着像铁丝编的。

修法是把三角形**外扩**。⚠️ 第一版"把顶点从面质心往外推"**对最关键的那条边几乎无效**：细长三角形的共享对角线，两端顶点的径向方向几乎**沿着**这条边，垂直位移接近零。正确做法是**三条边各自沿外法线外移，再求交点**。

**二、外扩必须封顶。** 近退化三角形（圆柱轮廓附近满是这种）的两条边近乎平行，偏移线的交点跑到几百像素之外——第一版只挡住了"恰好平行"，结果模型上炸出一片长针。位移超过 `6d` 就放弃外扩、把顶点留在原处：代价只是那一条边上重新出现细缝，比针刺好得多。

## 8. 本轮**不做**什么

纹理、阴影、透视正确插值、高光、动画、多光源（只有一盏**固定在相机空间**的方向光 + 环境项）、剖切、层级场景图。

不是待办，是判断。工控三维示意图的语义载体是**形状 + 位置 + 状态色**，操作员在这块屏幕上只回答一个问题——"哪台泵红了"。纹理和阴影**消耗对比度**，而状态色正是需要对比度的那个东西。光固定在相机空间，是为了转动模型时整体明暗不漂——**变色的必须是状态变了的那个部件，不能是别的**。
