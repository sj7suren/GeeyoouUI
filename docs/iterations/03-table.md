## 1. 唯一一处真正的架构分叉：单元格是控件还是像素

三个方案摆在一起：

| | 做法 | 结局 |
|---|---|---|
| A | 每个可见单元格挂真实子控件，随滚动回收复用 | **否决** |
| B | 单元格全部画出来；只有进入编辑态时，把**唯一一个**复用的编辑器移过去 | **采纳** |
| C | 静态呈现画出来，交互型（Switch / CheckBox）挂真控件 | 否决 |

否决 A 的三条理由，按权重：

1. **门 lint 直接判死。** `add<T>` / `removeChild` / `setGeometry` / `setVisible` 全是 P2 门（§11.4）。回收复用意味着**每滚动一帧在循环里开几十道门**，且门后必然还有代码——一次滚轮就制造几十个未归档候选。这不是"多登记几行"，是把 §11.4 灌成垃圾场。
2. **违反「数据不复制」。** 一个 `CheckBox` 子控件自带 `checked_`，那就是模型已经持有的真值的**第二份拷贝**。它存在的那一刻起，拉取模型就变成了推送模型，外加一个等着发作的同步缺陷。
3. **画出来的单元格滚过去是零成本。** 20 万行只画屏幕上的那二十来行。

C 拿到 A 的全部成本，只省掉画开关的十几行——而 `CheckBox` / `ToggleSwitch` 不过是圆角矩形加一个圆，现有 `Painter` 绰绰有余。

**四个编辑器是这条规则唯一的例外，且例外本身证明规则**：一个 `LineEdit`、一个 `SpinBox`、一个 `ComboBox`、一个 `MultiSelect`，**构造期建好，运行期永不增删**。一张有一千个可编辑单元格的表，自始至终只拥有四个控件。

## 2. 一次被推翻又被推回的裁定（值得记下来的过程）

`TableModel` 该是**抽象基类**还是 **`std::function` 回调包**？研发中心先裁 A（抽象基类），我提出反对，裁定改判为回调包，我核实后发现自己的反对**量级算错了**，裁定又改回抽象基类。三步都记在这里，因为**中间那一步的错误比结论更有教育意义**。

* **我的反对**：门谓词 P1 是**按名字全库生成**的（lint 从 `include/geeyoou/**` 收集所有虚函数名，再在 `src/` 按名字 grep 调用点）。所以 `TableModel` 一旦声明 `virtual tableText()`，`TableView.cpp` 里每一处 `model_->tableText()` 都是 P1 门——而拉取模型的全部意义就是**在绘制中途取值**，于是 `onPaint` 必然充满门。
* **我算错的地方**：我说"一屏几十行 × 十列 = 几百个候选点"。**错了**。lint 的键是 **(文件, 函数)**，不是调用点。`ProgressBar.cpp（onPaint）| P1 styleState | 1` 就是同一个形状，全库照此办理已经出货很久。`TableView.cpp` 实际新增 **7 行**登记，不是几百行。
* **最终裁定，理由比"代价可接受"强一层**：改用 `std::function` 的真实效果是**把一道真门变成谓词看不见的门**——而这恰是本仓库反复复发的那个缺陷族。抽象基类让暴露面**可见、可定级、可复查**；闭包让它消失。**安全性上抽象基类胜，不只是省事。**

配套产物两条：

* 所有虚函数一律 `table*` 前缀。P1 名字集合是全库的，一个叫 `text()` 或 `rowCount()` 的虚函数会**把全库无关的同名调用一夜之间变成门候选**。这不是命名风格，是防止一个新类染红四十个文件。
* **§12.4 新登记 `PULL-1`**：`std::function` 回调进应用代码这一整类是**谓词的盲区**（P1 认虚名、P2 认封闭清单、P3 认 `.emit(`，回调一条都不匹配）。主语写的是**这一整类**，不是某个控件——`ListView` 早在 R1 就带着它出货了。**把主语写窄，正是这个缺陷族复发里至少两次的直接原因。**

## 3. 异步子节点：为什么是信号，不是拉取器

```
tree.setLazy(node, true);
tree.childrenRequested.connect([&](NodeId id) { pending.push_back(id); });   // 只记下，不阻塞
// …UI 线程上，答案到了：
tree.addNode(id, {...});
tree.finishLoad(id, true);
```

**刻意不提供**的是 `std::function<void(NodeId, Callback)>` 形态的拉取器。那个形状**读起来就像**回调可以在答案到达的那个线程上调用，而第一个这么做的人就写出了一个碰控件树的工作线程——`docs/architecture.md` §3.11 明令禁止、且是本库唯一无法事后补救的失败面。一个只回传 id 的信号**没法被这样误读**：根本没有回调可以在错误的线程上调。

节点状态四态 `Pending / Loading / Ready / Failed`。两条值得写死的行为：

* **失败是终态，不会自己重发。** 一个指向不可达站点的分支，否则会在每次重绘时重新发请求。
* **`expandAll()` 不碰 Pending 分支。** 否则一次菜单点击 = 对历史库的一次拒绝服务。

## 4. 合并单元格：负偏移契约

锚点格回答自己的跨度 `{2, 3}`；**被覆盖的格子回答指向锚点的负偏移** `{-1, 0}`。

负偏移这一半是合并在大表上**负担得起**的原因。替代方案是视图向上扫描直到找到锚点——那是每个绘制格上的无界工作量，20 万行的表上顶部有一处合并就意味着为了画一屏而扫完整列。**局部作答是模型永远做得到、视图永远做不到的事。**

配套两条硬边界：`setMaxSpan(n)`（默认 32）是回溯上限，越界按不合并画；默认**关闭**，关闭时模型一次都不会被问到——「不用不付代价」，架构 §4 的规则下沉一层。

## 5. 门禁纪律：这一轮实际用到的三种处置

初扫 **14 个**未归档候选，最终 **0**。三种处置各有其位，区别不是工作量，是**门后那段代码在干什么**：

| 处置 | 用在哪 | 例子 |
|---|---|---|
| **尾发射** | `emit` 能挪成函数最后一条语句 | `toggleSelection`、`tableToggleExpansion` |
| **抽尾调用** | 挪不动的，抽成只有一条语句的 `emitXxx()` | `TablePager::emitPage()` / `emitPageSize()` |
| **DeathWatch** | 门后真的还要干活，且门里是**写**应用存储 | `handlePress`、`beginEdit`、`endEdit`、`commitNumber` |
| **§11.4 登记** | 绘制期的**只读**拉取，受 `TableModel` 头注释的契约保护 | `paintCell`、`paintTreeCell`、`mergedAt` 等 7 条，family R |

⚠️ **`emit` 后面跟一个 `return;` 或一个 `break;` 就已经是「门后有代码」。** `TablePager::onMouse` 的四处 `emit` 全埋在 `switch` 的 `case` 里，每个后面都有 `break`——这是本轮第一次真正用上「抽尾调用」。

## 6. ASan 抓到的那个缺陷，以及为什么它的修法值得单独写一节

**症状**：`showcase_pages.the_tables_basic_page` 用例在 `Widget content` 析构时崩在 `Layout::arrangeFor`，access violation。

**根因**：`TableView` 用**裸指针**读模型，所以表必须先于模型死。而模型如果是 `Widget` 子类的**普通成员**，顺序恰好反了——**成员先于基类销毁**，模型先走，随后 `~Widget` 才去销毁那个指着它的表。

**第一次修，崩得更响**：在析构函数里写 `removeChild(table_)`，"手工先销毁读者"。`removeChild` 是**树操作**：它标脏布局链，于是一趟布局在**已经销毁到一半的祖先链**上跑了起来——因为这个面板本来就是作为父节点 teardown 的一部分才在析构的。

**结论两条，第二条是修法**：

1. **析构期不得碰树。** 不 `removeChild`，不 `setVisible`，不 `setModel(nullptr)`——任何会向上走父链或触发布局的调用都不行。
2. **顺序向语言要，不要向记性要。** 把模型放进一个只为占位而存在的基类：

```cpp
class TableModelHolder { protected: std::unique_ptr<TableModel> model_; };
class TablePanel : public TableModelHolder, public Widget { ... };
```

销毁顺序是「析构体 → 成员（逆声明序）→ **基类（逆声明序）**」，于是 `~Widget`（销毁作为子控件的表）先跑，`~TableModelHolder`（销毁模型）后跑。**读者先于被读之物死亡，由构造保证，而不是由谁记得住保证。** `AsyncTreePanel` 同形同修。

`~AsyncTreePanel` 里**唯一**保留的动作是 `platform().stopTimer()`——那不是树操作，而是把一个捕获了 `this` 的回调从事件循环上摘下来，是"面板被销毁了"和"下一次 tick 打进已释放内存"的分界。

## 6.5 离屏复核抓到的两条（测试全绿之后才发现的）

门禁绿了不等于看起来对。七个页面各渲染一张 PNG 之后，有两条是**测试永远抓不到、只有眼睛能抓到**的：

**一、树的分组行画出了一个「关」状态的开关。** 分组行没有「投用」这个值，`tableFlag` 返回 `false` 是"没有值"的默认，而不是"值为假"——视图分不出这两者，就画了一个**看起来可操作、实则什么都不代表**的控件。比空白格更糟：空白格是诚实的。
修法：`TableModel::tableCellPresent(row, col)`。树模型天然答得出——**节点在这一列存过值没有**。`Check` / `Switch` / `Progress` 三种字形单元格问一次，不存在就什么都不画，且**不画的格子也不可点**（否则就是同一个缺陷换顶帽子）。

**二、`删除` 的红色是建页时从主题里抓下来的。** `CellAction` 原本带一个 `Color` 字段，示例写的是 `Theme::current().danger`——那是**建页那一刻恰好生效的皮肤**。切到浅色皮肤，每个删除链接都还是深色皮肤的红，落在白底行上。这个坑这个仓库已经付过一次学费（`ShowcaseWindow.cpp` 开头那段 NOTE 讲的就是标题栏）。
修法：`CellAction` **只带语义不带颜色**（`Tone::Link / Danger / Muted`），颜色由视图在**绘制时**对着活着的主题解析。同一条毛病在树节点上也有一份（`setAccent(Theme::current().success)`），示例改用 `StatusTreeModel` 覆写 `tableAccent`，从状态词现算。

两条都不是"样式问题"。第一条是**语义错误**，第二条是**已知会复发的缺陷族的第 N 次**。
